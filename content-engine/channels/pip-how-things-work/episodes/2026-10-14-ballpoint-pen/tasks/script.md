# Skill: write-script

You receive a task file with the channel, the series, its characters, the channel's learnings, the idea, and the
SKILL.md of every render skill the series uses. You write **one file: `script.json`**. Nothing else.

## How to write it

1. **Follow the series.** Use its beats, in order, with the same ids. Each beat's `purpose` says what it must do;
   `seconds` is a target — the voice decides the real timing.
2. **Hook first.** The first sentence of the first beat is ~5 words and lands within 2 seconds. Put the hook on
   screen too (`on_screen_text`, ≤ 30 characters works best). Questions and surprising claims work; greetings don't.
3. **Write for the ear.** Short sentences. Contractions. One idea per sentence. Numbers the way people say them.
   Read it out loud in your head at the character's speed. Total words are given in the task — stay inside them.
4. **Be the character.** Use its personality, vocabulary and verbal tics from its file. A catchphrase at most once.
5. **Show, don't decorate.** Every beat has a visual that explains what is being said (see the render skills).
6. **Facts are claims.** Every fact — spoken, on screen, in a part label, or a number in a graphic — goes into
   `claims` with a real source you have checked. Unverifiable → cut it. Confidence `low` → find a better source.
7. **Pronunciations.** If the voice may stumble (years, acronyms, names, symbols), add
   `"pronunciations": {"1938": "nineteen thirty-eight", "LED": "L E D"}`. Captions still show the original word.
8. **No AI-label text, no links, no "subscribe" unless the series' `cta` asks for it.**

# Skill: render-3d-explainer

A scene skill: during the beats that use it, it fills the frame. You describe the object once as simple
low-poly parts in `script.visuals["render-3d-explainer"]`, then direct each beat with a *shot*. Framing is
automatic (the engine fits the parts into the frame around the headline, captions and character), so you never
give camera coordinates.

## Scene payload: `visuals["render-3d-explainer"]`

```jsonc
{
  "object": "flashlight",
  "background": { "top": "#0d1b2a", "bottom": "#1b263b" },   // optional; defaults to the channel brand
  "parts": [
    {
      "id": "body",                    // unique, lowercase-with-dashes
      "label": "Aluminium body",       // callout text, ≤ 26 chars (shown on screen → it's a claim if factual)
      "note": "keeps it all aligned",  // optional second line, ≤ 34 chars
      "shape": "tube",                 // cylinder | tube | cone | sphere | box | capsule | torus | spring | disc
      "radius": 1.6, "inner_radius": 1.35, "length": 12,        // size fields depend on the shape (below)
      "position": [0, 0, 0],           // centre of the part when assembled, in cm
      "rotation": [0, 0, 0],           // optional, degrees around X, Y, Z
      "color": "#3d5afe",
      "material": "metal",             // plastic | metal | glass | rubber | ink | paper | wood | fabric
      "opacity": 1,                    // optional
      "shell": true,                   // outer casing: turns see-through when the camera flies inside
      "explode": [0, 0, -4],           // where it moves when fully exploded (offset in cm)
      "anchor": [0, 5, 0]              // optional: where the callout line points, relative to the centre
    }
  ]
}
```

**Coordinates:** centimetres, real proportions, **Y is up and is the object's long axis** (vertical video → stand
long objects upright). X is right, Z is towards the viewer. Positions are part centres in the assembled object.

**Sizes per shape**

| shape | needs | notes |
|---|---|---|
| `cylinder` | `radius`, `length` | optional `radius_top` / `radius_bottom` for a taper |
| `tube` | `radius`, `inner_radius`, `length` | hollow; great for barrels and casings |
| `cone` | `length`, `radius_bottom` (+ optional `radius_top`) | tips, nozzles |
| `sphere` | `radius` | low-poly ball |
| `box` | `width` (X), `height` (Y), `depth` (Z) | clips, buttons, boards |
| `capsule` | `radius`, `length` | length includes the rounded ends |
| `torus` | `radius`, `tube_radius` | ring around the Y axis (washers, O-rings) |
| `spring` | `radius`, `length`, `turns` (+ optional `wire`) | coil along Y |
| `disc` | `radius` (+ optional `length` = thickness) | lenses, caps, coins |

Keep it simple: 5–12 parts, real proportions, contrasting colours for parts that sit next to each other.
Very small parts (a 1 mm ball in a 14 cm pen) are fine — the camera can fly to them.

## Beat visuals: `beats[].visual`

```jsonc
{ "skill": "render-3d-explainer", "shot": "fly-in", "target": "spring", "callouts": ["spring", "battery"], "explode": 0 }
```

| shot | what the camera does | needs |
|---|---|---|
| `establish` | the whole assembled object, slow orbit | — |
| `fly-in` | flies close to (and into) a part; shells turn see-through | `target` |
| `explode` | parts fly apart along their `explode` offsets; camera pulls back to show all | — (`explode` 0–1 optional) |
| `focus` | frames one part (assembled or exploded), others dim | `target` |
| `reassemble` | parts come back together | — |
| `orbit` | keeps the framing and circles around | — |

- `callouts`: up to 4 part ids labelled during the beat (fewer is better: 1–3). They appear one by one after the
  beat's voice starts; keep labels short.
- `explode` (0 = assembled … 1 = fully exploded) sets the state the beat ends in; it carries into later beats.
- A typical arc: `establish` (hook) → `fly-in` (the mystery) → `explode` (show the parts) → `focus` (the key part,
  1–2 times) → `reassemble` or `orbit` (payoff).

## Good explode views

- Explode mostly along the long axis (Y), with small sideways offsets so parts don't hide each other.
- Total exploded height ≈ 1.6–2× the object; small parts can move further so they're visible.
- Outer casings (`shell: true`) usually move backwards (−Z) or sideways so the inside is revealed.

## Per beat: `beats[].character`

### Expressions (same fields for every rig; all optional)

| field | range | effect |
|---|---|---|
| `eye_scale` | 0.5–1.6 | bigger / smaller eyes |
| `pupil_scale` | 0.4–1.6 | tiny pupils = surprise |
| `lid` | 0–0.9 | half-closed eyes (sleepy, sceptical) |
| `tilt_deg` | -25–25 | head tilt |
| `look` | [-1..1, -1..1] | gaze direction |
| `bounce` | 0–1 | how much it bobs while talking |
| `brow` | flat \| up \| down \| worried | brows (2D rig) |
| `mouth_curve` | -1–1 | frown … smile (2D rig) |
| `glow` | 0–1.5 | eye/LED glow (robot rig) |

# Skill: captions

Captions are generated, not written: you don't add anything to the script for them. They show the voiceover
exactly as written in `script.json` (so spelling and capitalisation there are what viewers read), a short page at a
time (≤ 2 lines), and highlight each word while it is spoken.

## How it works

- **Timings** come from the voice step (`audio/timings.json`). The local voice (Kokoro) predicts how long every
  phoneme lasts before generating audio; the engine reads those durations, so each word's start/end is exact — no
  speech recognition, no drift.
- **Pages** break at sentence ends and beat boundaries, and when a line would get too wide for the safe area.
- **Style** comes from the channel's brand: `font`, `accent_color` (highlight), `text_color`, `caption_case`
  (`upper` for ALL-CAPS captions). Captions sit in the lower part of the safe area, above platform UI.

## What this means for the script writer

- Write numbers and names the way they should appear on screen; add `pronunciations` if the voice should say
  them differently (`"1938": "nineteen thirty-eight"`).
- Very long words (14+ letters) get a line to themselves; prefer shorter words.
- Punctuation shows on screen. Use "—" and "…" sparingly; they also create pauses in the voice.

## QA

`workflows/qa.md` checks that caption words equal the script, the highlighted word matches the timings on ≥ 98 %
of frames, no word is shown over silence, and captions never leave the safe area or overflow.
